# OSCAR Ascend 端到端慢速分析、改进计划与加速预期

- 日期：2026-09-08
- 分析代码：`ac94f31c0b26ae440e3ab200875e458cd77b21d6`，分支 `acc_ok_but_slow`
- 目标环境：vllm 0.23.0 + vllm-ascend **0.23.1.dev0+g5cb98caaa.d20260822**，Qwen3.5-27B W8A8 + MTP、TP4，用户日志为 Ascend910B4。

本文基于仓库代码、提供的 reference、用户完整评测摘要及历次 NPU PERF/A/B 输出。没有本地 NPU；下面的未来加速范围是带前提的工程估计，不是已经实现的结果。本次只提交分析文档，不把新实验改成默认计算路径。

## 1. 结论与差距

**当前实现仍然远慢于 base，不能称为性能适配完成。核心问题是：压缩缓存外面套了一条昂贵的“逐请求重建完整历史，再调用原生 attention”的执行路径。** 原生 attention 本身已经很快，围绕它的数据准备、调度和重复工作没有消失。

| 用户提供的指标 | OSCAR | base，不开 OSCAR |
|---|---:|---:|
| 完成样本 | 127 | 120 |
| 进度条总耗时 | 1:27:59 = 5279 s | 10:15 = 615 s |
| 总耗时比 | **8.58×** | 1× |
| 总耗时 / 样本数 | 41.57 s/case | 5.125 s/case |
| 按样本数粗归一化后的耗时比 | **8.11×** | 1× |
| API infer task elapsed | 5383.57 s | 未提供同口径值 |
| 请求失败数 | 0 | 此摘要未提供 |
| LongBenchv2 accuracy | 50.3937%，即64/127 | 未提供 |

解释边界：

- 127和120不是同一批完整样本；上面的8.11倍是按例粗归一化，尚未按输入/输出token量归一化。这不否认巨大差距，但不能作为严格的token吞吐倍率。
- 41.57 s/case是并发任务总墙钟时间的摊销，**不是平均请求延迟，也不是TPOT**。
- API计时比进度条计时多约104.6秒，两者边界不同；不能把后续7.40秒的评估时间混进推理时间。
- FAIL=0证明请求完成，不证明任务质量合格。只有OSCAR准确率，尚不能判断相对base的精度损失。
- 即使请求参数相同，量化也可能改变EOS位置和生成长度。需要总输出token数和每例长度分布，才能拆开“每token更慢”与“生成了更多token”。目前没有证据认定后者已发生。

**预计改善：近期可规划的单请求模型执行目标约1.25–1.5×；整任务暂以1.3–2.0×作为条件性工程目标。当前没有足够证据承诺恢复base所需的约8倍改善。** 第6节给出推导和时间换算。

## 3. 当前代码具体慢在哪里

### 3.1 每个请求、每一层、每一步都重新物化历史KV

对于已有历史、当前又有新K/V的MTP/DecodeOnly，当前默认流程是：

```mermaid
flowchart LR
  A[本步新K/V] --> B[旋转、裁剪、写INT2缓存]
  B --> C[窗口筛选与staging写入]
  C --> D[逐请求循环]
  D --> E[完整历史反量化为FP16]
  E --> F[读取staging并覆盖窗口]
  F --> G[转BF16并拼接当前K/V]
  G --> H[单请求原生融合attention]
  H --> I[输出逆旋转]
```

这个流程在每个rank的16个FULL层重复；CPU路径保留参考算法。prefix=0时不做历史反量化，本文不把这部分成本算到无缓存首段prefill上。

直接证据：

- [`forward`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/backend.py#L239)先写INT2、更新staging，再选择读取路径。
- [`_prefill_attention`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/backend.py#L361)在Python中逐请求调用`oscar_full_dequant`、`_stage_splice`和`oscar_prefill`。
- [`npu_prefill`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/kernels/prefill.py#L21)拼接历史与当前K/V；原生调用收到的`actual_seq_lengths`、`actual_seq_lengths_kv`各只有一个请求的长度。

原生reference的`_get_fia_params`和`forward_fused_infer_attention`则可以把整批页表、缓存和长度传给原生分页attention。**当前OSCAR增加了一遍完整解码/写回，并拆散了整批调用。** 已采用“原生融合算子”不等于恢复了“原生批量分页执行路径”。

### 3.2 反量化任务粒度很小，并发会放大重复工作

[`oscar_full_dequant_triton`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/kernels/dequant_kernel.py#L78)按页向上取整分配FP16 K/V，网格是`(alloc_len, Hk)`；内核中`program_id(0)`对应一个历史token，每个program读取页号、元数据和压缩字节。

按已知形状作工作量示例，**不是实测并发耗时**：

- 每rank16个FULL层，32个请求，每请求约24K历史，Hk=1。
- 一步中有约`16 × 32 = 512`次历史反量化调用，以及约512次单请求原生attention调用。
- 反量化逻辑program数约`16 × 32 × 24576 = 12,582,912`。
- 这不是1258万个kernel launch，也不是物理线程数；不能混淆逻辑program和主机启动次数。
- 一个请求的FP16 K+V历史约24 MiB；32请求每层约768 MiB，16层仅反量化输出的逻辑写入量就约12 GiB/步。attention还要消费这些数据，且另有窗口覆盖、类型转换和拼接。实际HBM流量受缓存和实现影响，不能直接等同于这个逻辑字节量。

原生attention也要读取历史；OSCAR的额外问题是先把它完整重建、写入临时缓冲，再读取。KV压缩省了常驻容量，却增加了解包与临时数据流量。

### 3.3 小窗口的拼接实现仍按整个历史长度搬运

[`_stage_splice`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/backend.py#L483)为全部历史页读取owner，并通过`stage_k[rows]`、`stage_v[rows]`生成按历史页展开的张量，然后`torch.where`覆盖缓存。

即使真正有效的sink/recent很小，当前实现仍会沿全历史做gather、类型转换和where。后面的FP16→BF16、`cat`又产生完整历史规模的数据操作。函数调用不多，并不代表只有几个很小的算子。

### 3.4 staging元数据和旋转在层间、路径间重复

[`_staging_write`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/backend.py#L439)每层重新构造request/position、过滤slot、排序、选最后writer和窗口token，再更新该层arena。

- `nonzero`和布尔索引产生动态长度结果，存在主机等待/分配成本；实际同步位置要用设备trace确认，不能把每个`.numel()`都一概算作同步。
- 对共享元数据和相同几何的FULL层，writer选择计划存在复用机会；但**每层KV值和owner状态不能直接共享**。
- [`do_kv_cache_update`](https://github.com/jpl123123/oscar/blob/ac94f31/oscar_ascend/backend.py#L150)已经计算旋转后的K/V；staging和有历史的attention又旋转本步K/V。可以复用未裁剪的旋转结果，但必须保留“窗口不裁剪、不量化”的语义。
- 裁剪排序是另一项工作，不能和staging的槽排序混为一谈。

### 3.5 常驻压缩比例不是加速比例

D=256时：

| 内容 | K+V字节/token·head |
|---|---:|
| 原生BF16 | 1024 B |
| OSCAR逻辑payload | 160 B |
| 当前packed物理槽 | 512 B |

因此FULL KV物理槽密度约为2倍，不是逻辑payload推得的6.4倍；更不是整机吞吐倍数。MTP影子池、FP32 staging、旋转矩阵还会占常驻容量，已有预算代码负责计入。

日志中“写入开销 -84.4%”来自逻辑字节比，**不能解读为写入耗时下降84.4%或整机显存节省84.4%**。

## 4. 实测证据支持什么、不支持什么

### 4.1 稳定默认路径的单请求分解

取已有PERF中重复4-token MTP步骤的近似值。它采用同步墙钟计时，含主机调度成本；这些比例不是无诊断状态下的纯设备时间。

| 不重叠的粗分类 | 16层/单步耗时 | 占execute_model |
|---|---:|---:|
| 读取路径`prefill_attention` | 197 ms | 35.4% |
| staging更新 | 53 ms | 9.5% |
| INT2写路径，含旋转/裁剪 | 25 ms | 4.5% |
| 其余OSCAR forward开销，约数 | 4 ms | 0.7% |
| OSCAR forward以外的模型执行 | 277 ms | 49.8% |
| **execute_model** | **556 ms** | **100%** |
| 另计sample_tokens | 约35 ms | 不在上述556 ms内 |

读取路径内的原生调用约8.4 ms，进入它之前等待已提交操作约165.7 ms；两者都在上述197 ms的范围内，不能再次相加到总数。约1.9 ms的staging排序包含在53 ms内；约7.7 ms的旋转/裁剪包含在写路径内。

这证明当前应优先看KV准备及其并发放大，而不是继续优化已很快的原生attention本体。也证明排序不是全部性能差距的解释。

### 4.2 已失败的实验不能继续计作未来收益

| 实验 | 实测结果 | 当前决定 |
|---|---|---|
| 自写向量paged | 16层约4.35 s，占当时模型执行约92% | 默认关闭 |
| paged tile 4→32 | 目标910B4出现UB溢出、编译重试失败 | 不提升默认值 |
| KV准备融合，同进程MTP A/B | 基线28.233 ms，候选28.637 ms | 没有收益证据 |
| KV准备融合，同进程continuation A/B | 基线83.903 ms，候选93.751 ms | 保留基线 |

A/B各6个样本波动较大，不能声称差异统计显著；但结果足以拒绝“候选已提速”的结论。已经获得的4.72 s→0.556 s局部改善不能再乘到未来预测上。

此前我先按结构推测优化、再让用户运行门禁，没有先取得完整并发和设备时间证据；数值PASS不等于优化成立。这造成了不必要的试错，后续默认配置必须同时接受数值、速度、显存和质量验收。

### 4.3 尚不能确定的因素

1. **并发实际耗时分布**：APIServer的Running不是该步实际调度数。当前单请求PERF不能证明32并发时仍是同样比例；`./load`已能采集并发短步。
2. **生成token量与尾部请求**：整批127例缺总输入/输出token数、每例长度、finish_reason及请求时间。不能把额外生成或少数长尾请求当作已证实原因。
3. **base的完整执行配置**：按用户“其余相同”的说明分析；但仍应保存两份完整启动命令。当前脚本强制target与MTP eager、采用int8物理KV槽；没有base启动记录，不能凭空把差距归因于graph设置。
4. **约10秒首次准备耗时**：可能涉及未预热特化，也可能有其他初始化/等待。没有编译事件trace，不能说全部都是JIT，更不能解释整场88分钟。
5. **GDN整数ArgSort、HDK padding、内部格式warning**：日志或reference中确实存在，但不能据此证明它们是主要瓶颈。GDN也有整数排序；当前staging槽排序已经在安全范围内用FP32。
6. **CPU、设备频率和其他负载**：A/B有较大波动，需设备trace和运行环境快照确认，不预先归因。

## 5. 我打算怎样改进

以下是实施计划，尚未完成的内容不算已交付性能。保留`USE_PAGED=0`、`FUSED_PREP=0`作为对照；不改用户指定的框架版本。

### P0：固定可复现的完整基线，不再用不同边界的数字推算

- base与OSCAR运行同一份127个样本ID、同一提示词/生成参数/seed/最大输出长度和32并发；保存输出与finish_reason。
- 固定模型、旋转文件、源码hash、驱动/CANN、设备列表、CPU绑定、eager设置；归档启动命令。
- 记录总输入/输出token、端到端总时长、TTFT/TPOT分布、稳定生成吞吐、最大显存和MTP接受率；每种配置至少重复3轮。
- 小算子实验先跑同进程交错A/B，至少20次预热后的样本并检查离散程度；最终仍以整批评测为准。
- 用并发PERF及设备trace区分host launch/同步、实际kernel执行、通信和KV准备。诊断轮不作为正式吞吐成绩。

这一步的速度收益按0计；它决定后续优化是否真实。

### P1：减少重复的控制工作和旋转，先做可验证的局部改造

涉及`backend.py`的写路径、staging及metadata读取。

1. 在一个明确的forward生命周期内，按KV组和几何生成一次slot/window/writer选择计划，供对应FULL层使用。不能按旧tensor地址无限缓存；需要明确step标识，禁止跨步、跨不同slot映射复用。
2. 保留每层独立的owner/arena，复用的只是索引计划。验证block回收、碰撞、MTP拒绝后重写及负slot。
3. 每层只计算一次本步未裁剪的旋转K/V，写路径在其基础上裁剪量化，staging和attention复用未裁剪结果。约束额外临时内存，不保留16层的全部本步副本。
4. 把必要的动态长度发现集中到共享准备阶段，减少每层重复`nonzero`/布尔索引及小算子启动。

**工程目标**：在已测单请求场景，staging的53 ms争取降到约10–20 ms、写路径25 ms争取降到约15–20 ms。它不是数倍模型加速：两项一起约为模型执行1.05–1.15×的量级，需真机证实。

### P2：内存受限的多请求KV准备和批量原生attention

涉及`_prefill_attention`、`prefill.py`、反量化实现及`integration.py`预算。

1. 将短MTP请求按历史KV总token数分组，不按请求数盲目固定全批。把相同组的Q/K/V旋转和metadata准备批量化。
2. 为组内请求构建累计query/KV长度，使用TND保持每请求独立的右对齐因果边界；保留原token顺序映射和padding处理。reference已有dense TND累计长度的用法。
3. 基于页表做批量、页内连续的历史准备，避免逐token重复页号读取，并减少主机上逐请求启动。必须先检查生成IR和UB占用，不重复“直接放大tile”的做法。
4. **不能只把attention调用合并**：原生算子本体已很快。若KV准备仍逐请求同样昂贵，批量attention不会凭空产生数倍收益。
5. 设定每worker总workspace预算，初始以128–256 MiB量级做实验，并实测所有临时张量峰值。32×24K的K+V输出本身就约768 MiB，不能直接整批拼接；输出缓冲上限也不等于总峰值。
6. 工作区按worker/执行流管理，在预算确定前预留；不能为16层各常驻一份大缓冲。流间依赖、复用时机和异步调度必须验证。

**工程目标**：将已测197 ms读取区间降低到约70–120 ms作为原型验收目标，而非预测事实。并发下要求kernel/host调用数按分组下降，且32并发端到端提升有重复实验支持。

### P3：若仍大幅落后，做压缩KV感知的真正attention实现

P1/P2仍保留dense历史准备，其结构性上限不会消失。要进一步逼近base，需要更深入的实现：

- 从INT2分页缓存按tile读取，在片上解包并参与QK/PV计算，避免每步完整历史写回GM再读一遍。
- 针对已知GQA=6:1、MTP q_len=4，让同一KV tile在多个Q head/query之间复用，采用适合Ascend矩阵计算单元的分块；不能沿用当前逐query/head向量循环的低效组织。
- 窗口和当前chunk继续使用未量化值，softmax归一化、跨split归并和因果可见范围必须一致。
- 先以D256、Hk1及实际短MTP形状实现可测原型，再扩展形状；评估AscendC或适合目标后端的Triton矩阵路径，需要目标机器的IR、设备trace和性能数据。

这是算子重构，不是一两个环境变量的调整。**目前不为这一阶段承诺固定倍数，也不将其算入近期收益。** 原型不同时优于基线的速度、显存和质量，就不进入默认路径。

### P4：最后处理执行模式和框架剩余开销

已测单请求仍有约277 ms在OSCAR forward之外，另有约35 ms采样。需要定位其中的模型其他层、通信、GDN、CPU调度和同步，而不是都算成不可优化或都算给OSCAR。

图捕获只有在移出数据相关Python控制流、固定工作区并验证缓存更新生命周期后才评估。若比较graph模式，base也要按同样规则运行；不能通过只改变一边配置宣称插件追平。

## 6. 预计能快多少倍：用预算约束，不叠乘口号

### 6.1 单请求已有数据给出的上限

采用近似分解：

```text
T_execute = 277（OSCAR以外）+ 197（读）+ 53（staging）+ 25（写）+ 4（其他）
          = 556 ms
```

| 假设优化 | 单步新耗时 | execute_model加速 | 含35 ms采样后的加速 |
|---|---:|---:|---:|
| staging→20 ms，写→18 ms，读不变 | 516 ms | 1.08× | 1.07× |
| 再把读→120 ms | 439 ms | 1.27× | 1.25× |
| 再把读→100 ms | 419 ms | 1.33× | 1.30× |
| 较进取：读→70、staging→10、写→15 ms | 376 ms | 1.48× | 1.44× |
| 不现实的上限：整个279 ms OSCAR forward消失 | 277 ms | 2.01× | 1.89× |

表内“降到多少ms”是工程目标假设，尚无新实现支持，不是测量值。它说明：**在这个已测单请求场景里，只动OSCAR forward，不可能再得到8倍整体执行提升。**

这个上限不适用于整个32并发评测：并发下逐请求准备可能占更大比例。需要`./load`给出相应占比，才能更新预测。

### 6.2 整任务的条件性规划范围

若并发测得可优化部分占比为f，该部分加速s倍，则：

```text
整体加速 S = 1 / ((1 - f) + f / s)
```

例如f=0.65、s=3时约1.76×；f=0.80、s=4时约2.5×。**这两个f目前没有被本任务的并发PERF证实，不能直接拿来报成果。**

我的当前预期分级：

| 层级 | 相对当前稳定默认的预期 | 条件与可信度 |
|---|---|---|
| P1+P2，单请求模型执行 | 约1.25–1.5×工程目标 | 有现有耗时分解约束；实现后的ms目标仍待测 |
| P1+P2，完整并发任务 | **暂按1.3–2.0×规划** | 低至中等置信，要求并发确实受重复准备/调用限制且输出工作量相近 |
| 3×及以上整任务改善 | 暂不承诺 | 需要P3/P4或新的并发占比证据，不能从现有局部数据推出 |
| 追平base，约8.1×粗归一化改善 | 当前无法承诺 | 不应把已获得的旧paged→当前改善再乘一次 |

仍需先给ac94f31稳定默认跑出同一127例的正式基线T0。若只为了排期，暂以用户本轮5279秒作参照，时间换算如下，**不是该版本必然完成时间**：

| 假设端到端加速 | 127例约需时间 |
|---|---:|
| 1.3× | 67.7分钟 |
| 1.5× | 58.7分钟 |
| 1.8× | 48.9分钟 |
| 2.0× | 44.0分钟 |
| 3.0× | 29.3分钟，未承诺 |
| 约8.11× | 10.85分钟，接近按127例粗换算的base，当前没有依据承诺 |

近期若只能获得1.3–2倍，仍然不等于追平base；这是必须如实承认的工程差距。

## 7. 验收规则和执行顺序

1. **保留已测基线**：当前不重新开启两个失败的实验默认值。先完成匹配数据集与配置的base/OSCAR对照，采集并发短步分段和设备trace。
2. **实现P1并单独验收**：检查索引计划复用、旋转复用，覆盖负slot、碰撞、请求结束、共享前缀、block回收、MTP连续拒绝/重写和padding。
3. **实现P2并单独验收**：覆盖并发1/8/32，历史1K/24K/64K及混合长短请求；验证请求隔离、因果边界、累计长度、预算和流间缓冲复用。
4. **性能晋级条件**：同进程预热A/B有稳定收益，目标形状不出现编译/运行失败；同127例至少3轮总时长和token吞吐确认改善，且p95延迟/峰值内存没有不可接受退化。作为工程门槛，默认切换应至少有约10%的可重复整任务收益；这是拟定的验收门槛，不是统计定理。
5. **质量条件**：保留base和OSCAR逐例输出，比较相同样本准确率及生成长度、EOS/截断原因。可完全复用语义的改动以原稳定实现为数值参考；改变累加/舍入路径的算子必须单列误差和任务质量。不得靠缩短输出、减少样本或关闭窗口来冒充加速。
6. **不满足就保留实验开关**：不把CPU测试PASS、NPU编译成功或一次更快的冷调用当作晋级依据。P1/P2若不足，再进入P3算子重构，明确新的风险和收益证据。

当前可用的短入口：`./bench`做单层同输入A/B；`./load`启动服务并等待并发短步诊断，负载仍由原客户端发送。它们是取证手段，不是性能问题已经解决的证明。
