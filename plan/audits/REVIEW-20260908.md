# OSCAR → vllm-ascend 0.23.0 系统性审查

审查日期：2026-09-08。范围：插件接入、缓存布局与生命周期、store/dequant/decode/prefill、MTP 影子池、校准及交付门禁。此次只新增审查材料，没有修改实现。

结论：当前代码具备量化格式和运行期接入原型，但不足以据此认定完成“正确、稳定且有效率的适配”。首要问题是窗口跨步状态丢失、参考写路径破坏无效槽语义、原生 metadata 的设备契约不匹配；性能主路径还在解压并逆旋转整个历史缓存。文档中的数值 PASS 与 ACTIVE 日志不能覆盖这些问题。

## 1. [P1] BF16 staging 每步重新分配，历史窗口全部丢失

位置：[backend.py:324](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/backend.py:324)。

`_ensure_staging()` 检查 `layer._oscar_stage_ready`，末尾却只设置 `self._oscar_stage_ready`。每次 forward 都会再次分配 stage K/V，并将 owner 全部清成 -1。第二次调用的 stage 对象变化、layer ready 标记仍不存在，已用提取的实际方法复现。

结果：decode 后过去的 sink/recent 不再保留；chunked prefill/MTP 每步 splice 也拿不到旧窗口。除精度保护失效外，默认 Hk=1、D=256、8192 staging tokens 的每层 K/V 约 8 MiB，16 层每步重复初始化约 128 MiB，另有 owner 和分配开销。

修复：统一状态归属，初始化成功后再设置 ready；添加跨至少三个 forward 的窗口保留测试，并覆盖 block 回收、碰撞、请求交错。OSCAR PR `oscar_attn.py:253–280` 正确地在 layer 上检查和设置 ready。

## 2. [P1] torch store 没有过滤负 slot，会覆盖末尾有效缓存

位置：[store_kernel.py:68](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/kernels/store_kernel.py:68)、同文件 82–95 行。

`oscar_store_ref()` 对所有 slot 计算偏移并 `index_put_`。以 bs=128、Hk=1、每槽512B 为例，slot=-1 得到偏移 -512；负索引指向最后一槽，不是 no-op。packed 256B 几何同样有此问题。Triton 分支明确 `if slot < 0: return`，两个实现的语义不一致。

原生 Ascend block table 在无效位置会生成 -1（`vllm_ascend/worker/block_table.py:272–276`）。默认 eager 且全为有效 slot 时不会触发；有无效槽、padding 或 Triton 失败降级时会暴露，可能影响另一请求。

修复：在参考写路径过滤有效槽及对应 K/V；验证 `[-1, valid, -1]` 的写入结果，要求无效项不改变任何字节，并逐字节对照 Triton。

## 3. [P1] DecodeOnly 误将原生 CPU seq_lens 当作 NPU Tensor 使用

位置：[backend.py:402](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/backend.py:402)、257–264 行。

reference `AscendAttentionMetadataBuilder.build()` 在普通路径从 `_seq_lens_cpu/seq_lens_cpu` 取长度，并直接填入 metadata 的 `seq_lens`（`attention_v1.py:291–298, 354–360`）。这个字段在该接口中不保证位于 NPU。

窗口 decode 只 `.to(torch.int64)`，不迁移设备，随后与 NPU 的 staged mask、arange 等混算；无窗口 Triton decode 则直接把这个 CPU tensor 传作设备指针。前者存在明确的跨设备运算错误，后者违反内核输入契约。probe 自己创建的是 NPU seq，无法检查到真实接缝差异。

修复：在边界明确维护 host 长度列表和 device 长度 tensor；使用原生 builder 产出的 metadata 做测试。实际 NPU 报错形式需真机确认。MTP 走其它状态时并不必然触发这一 decode 问题。

## 4. [P1] Triton decode 失败后的 torch 回退会再次崩溃

位置：[backend.py:268](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/backend.py:268)。

异常分支把 `oscar_decode_ref()` 的 `(out, lse)` 整个 tuple 赋给 `out_rot`，278 行随后 `torch.matmul(out_rot, ...)`。正常参考分支正确地写了 `out_rot, _ = ...`。对实际方法注入 Triton 失败，已复现 tuple 传给 matmul 的 TypeError。

修复：统一返回值解包；增加故障注入测试，确保 fallback 输出与直接 ref 相同。当前默认窗口分支会绕过这里，但此 fallback 是代码明确支持的路径。

## 5. [P1 / 性能] MTP 多 token 执行路径重建全历史 KV，抵消压缩带宽收益

位置：[backend.py:281](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/backend.py:281)、[decode_kernel.py:76](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/kernels/decode_kernel.py:76)。

forward 仅对 DecodeOnly 路由 fused decode；SpecDecoding 和 ChunkedPrefill 都进入 `_prefill_attention()`。该函数按请求 Python 循环，对每层每请求：全历史 INT2 → dense K/V → fp32 → 两次历史 K/V 逆旋转 → bf16 → concat → SDPA。reference runner 会给投机验证批次产生这些非 DecodeOnly 状态（`model_runner_v1.py:1477–1505`）。这不是“打开 USE_TRITON 就进入 fused decode”。

在 C=262144、Hk=1、D=256 的单请求单层，仅反量化 fp16 K/V 就是约 256 MiB；两个 `C×D` 乘 `D×D` 的历史逆旋转约 68.7 GFLOPs，16 层约 1.10 TFLOPs/步/rank，还未计 attention 和其它临时量。这是运算量估算，不是实测吞吐。

此外 `metadata_batch_lists()` 读取不存在于 AscendMetadata 的 `query_start_loc_cpu` 后，会退到 NPU `query_start_loc.tolist()`；builder 已有 `actual_seq_lengths_q` host 列表，插件却每层重新同步。decode wrapper 的 `seq_lens.max().item()` 也是同步点（当该 tensor 在设备上时）。README“热路径零 CPU 搬运”不成立。

修复方向：实现支持每请求多 query 的 paged INT2 attention，保留旋转域 K/V，只旋转新 Q 和最终输出；sink/recent 分段合并要保留原始 BF16 语义。prefill 采用适配 Ascend 的批量 attention 路径，host metadata 每步复用。先测 1K/8K/32K 上下文、并发1/8/32、MTP开/关的端到端和分段耗时，再判断瓶颈占比。

## 6. [P1 / 容量风险] MTP 影子池按整个 KV 池大小分配，未参与容量预算

位置：[mtp_shadow.py:32](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/mtp_shadow.py:32)。

首次拿到真实 int8 cache 后，为同形状的全部 K/V 创建 BF16 zeros，而非只为活跃 token 分配。reference `worker.py:527–597` 先 profile 再决定可用于 KV 的内存，`initialize_kv_cache` 在之后发生；插件没有为这个依赖最终 block 数的影子池修正预算。

因此默认 packed 模式存在首个真实执行/后续运行 OOM 风险，且“FULL 密度×2”不能直接解释为整机可服务容量×2。代码文档中 nb=1369、chunk=12 的示例约额外 2.0 GiB/rank（约2.15 GB，原注释把单位混为 GiB）；实际取决于分配日志。此次没有真机确认 OOM。

修复：让草稿 BF16 KV 成为 allocator 可计费的 cache group，或在求 block 数时把影子池作为每 block 成本计入；验证模型、KV、shadow、staging、峰值临时量之和。

## 7. [P1] 注入异常没有回滚，所谓 fail-soft 会留下半初始化实现

位置：[plugin.py:136](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/plugin.py:136)。

先修改 `impl.__class__`，再 `_oscar_setup()`；setup 如因不支持的 head_dim 抛出异常，except 只是记日志，没有恢复原类及部分状态。层仍是 OscarImpl，后续 forward 会访问未初始化字段。比如 D>256 会被 `check_d()` 拒绝，但 hybrid 判定此前没有过滤它。

修复：先验证兼容性/构造完整状态，再提交替换，或事务性恢复原类。packed 模式中不应声称可随意回到不理解该 dtype 的原生路径，无法安全恢复应中止启动。

## 8. [P2] probe 的 NaN 结果能被判成 PASS，且只测极窄内核夹具

位置：[probe_oscar.py:118](/Users/sunao2000/oscar_acc_ok_but_slow/delivery/probe_oscar.py:118)、102、168、178 行。

数值拒绝逻辑都是 `error > tolerance`。`float('nan') > tolerance` 为 False；Triton decode 全 NaN 时 `et` 也为 NaN，可打印 PASS。语言语义已复现。LSE 也未校验。

默认只写3个 token、单请求、第一页、连续槽，未覆盖跨页/非连续 block table、空段、padding、真实 metadata、连续窗口、MTP shadow 或 `_prefill_attention()`。所以内核 probe PASS 不等于 backend 集成 PASS。

修复：先断言输出与误差全部 finite；为合法空段 LSE=-inf 定义单独规则。增加上述实际接缝测试和故障注入。

## 9. [P2] ACTIVE 判定可放过“部分层成功、其它层失败”

位置：[check_oscar_active.sh:65](/Users/sunao2000/oscar_acc_ok_but_slow/delivery/check_oscar_active.sh:65)。

只要求 plugin/config/surgery 各出现至少一次，不校验 rank×目标层集合，不拒绝注入失败，不要求 packed 几何和 MTP shadow 成功。即使 16 层只有1层初始化成功，日志仍满足 ACTIVE。

修复：区分“已加载”与“完成集成验证”；从模型配置生成预期层集合，逐 rank 核验注入、dtype、geometry 和错误状态；实际读写另用明确的执行验证报告。不要把是否有 decode 日志作为 MTP 生效依据，因为它可能始终走 prefill 分支。

## 10. [P2] 安装器仅凭入口点存在跳过安装，可能测试新源码却运行旧插件

位置：[install_and_launch.sh:87](/Users/sunao2000/oscar_acc_ok_but_slow/delivery/install_and_launch.sh:87)。

`_ep_check` 只检查 entry point 名字，不验证它指向本仓库。机器已装旧 wheel 或另一个 checkout 的 editable 包时会跳过安装。指纹又对当前目录 `plugin.py` 求 hash，不能证明 worker 实际导入的代码相同；父进程当前目录的 import 还可能掩盖问题。

修复：验证 distribution/editable 路径，默认重新安装当前 checkout 的 no-deps editable；worker 启动日志报告实际 `__file__`、版本和关键文件 hash。

## 11. [P2] 几何检查把 token stride 当作每 head 槽宽

位置：[backend.py:162](/Users/sunao2000/oscar_acc_ok_but_slow/oscar_ascend/backend.py:162)。

对 `[nb,bs,Hk,D]`，`stride(1)` 是 Hk 个 head 的总宽度，`stride(2)` 才是每 head 槽宽。当前仅允许 stride(1)=D 或2D：Hk=2 packed 会误报 legacy，Hk=2 BF16 或 Hk=4 packed 会被错误拒绝。默认 TP4/Hk=1 恰好掩盖了它。

修复：区分 page/token/head stride，按每 head 检查容量，在检查通过后再设置 `_oscar_geo_ok`；增加 Hk=1/2/4 与两种 cache dtype 组合。若仅支持固定 TP4，应在启动时明确拒绝其它形态。

## 其它需要收口的事项

- **缺旋转文件并不会按提示降级。** `serve_oscar.sh:52` 对不存在的非空路径提示“单位阵降级”，`rotation.py:106–108` 却对非空路径直接 `_load_checkpoint(path)`；只有空字符串路径会返回单位阵。直接运行 serve 脚本或自定义路径错误时会在真实执行中 FileNotFoundError。应启动前验证完整 K/V 文件及目标层覆盖，明确选择失败或降级。
- **SCALE_FLOOR 在 fp16 中下溢为0。** `format.py:69–71` 将1e-8转half，IEEE fp16结果为0，常量向量量化会经过除0/NaN，跨后端整数转换不可靠。这个问题也存在于所提供的 OSCAR PR，不能因“对齐 reference”忽略。需约定常量向量编码，使用可表示的正 scale，并测零向量、常量和极小动态范围；本次未执行真实 PyTorch 转换测试。
- **版本约束过宽。** `pyproject.toml` 使用 `vllm>=0.23.0` 和 `vllm-ascend>=0.23.0`，插件却依赖私有 impl、metadata、KV 分配细节；交付自检只打印版本，没有声明/校验精确受支持组合。应区分纯0.23.0、带GDN补丁reference和实际vendor镜像。
- **校准代表性与完整性不足。** 生成器使用单段固定文本，只检查得到非空统计与非空 layers；没有要求所有目标 FULL 层/rank 齐全，也没有对应模型指纹。缺层加载静默用单位阵。这不证明目前质量一定低，但不能支持泛化精度已验收的结论。需要模型匹配、层覆盖检查和独立数据上的质量/接受率评测。
- **尚未关闭的缓存生命周期问题。** 修好 ready 后必须继续测物理 block 回收和 MTP 拒绝后的槽重写；staging owner 只识别物理块号，不能据此假定请求代际安全。本次不把尚未构造端到端复现的串数据场景计为已确认缺陷。

## 建议修复及验收顺序

1. 修复1–4、7，关闭缓存破坏、状态丢失与异常回退问题；同时修正probe的finite检查。
2. 构建真正的backend集成测试：多步window、跨页/非连续块、CPU seq metadata、不同q_len、padding、MTP验证/拒绝、影子池初始化；不要只重复同一量化格式的自对照。
3. 将shadow/staging计入真实显存预算，测试接近容量上限的持续并发；核对实际导入代码和每rank层集合。
4. 改造MTP执行路径，消除历史KV逆旋转和请求级串行调度；在同模型/上下文/并发/精度设置下对比原生BF16、legacy OSCAR、packed OSCAR。
5. 验收分别报告质量（任务分数、MTP接受率）、性能（TTFT、TPOT、吞吐和分段profile）、容量（可驻留token、峰值内存），不要用内核字节一致性替代这些指标。
